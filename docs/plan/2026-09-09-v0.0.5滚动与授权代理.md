# v0.0.5 聊天区自动滚动 + 工具授权代理到前端 (E-bot)

> 状态: 已确认设计 / 待开发
> 创建: 2026-09-09
> 来源: FEATURE_CHANGE(体验优化) + BUG_FIX(权限被静默拒绝)

## 1. 背景

v0.0.4 已完成:数据查询项目、超时容错、重试、E-bot 命名。当前使用暴露两个问题:

1. **聊天区不跟随输出滚动**。`.chatbox` 是固定高度 `max-height:46vh; overflow-y:auto` 的容器,但流式返回时从不滚动。答案逐 token 变长后内容溢出到可视区下方,用户只能看到开头几行,必须手动拖滚动条。长回答体验很差。

2. **分身调用工具时被静默拒绝**。后端用 `claude -p --output-format stream-json` 运行分身,分身读授权目录外的文件、或执行 `Bash` 等需要授权的工具时,CLI 在非交互模式下**没有任何人能批准,直接自动拒绝**。实测证据(`--permission-prompts host`,无 hook):

   ```
   TOOL_USE Bash {"command":"curl -s http://127.0.0.1:8080/api/db/databases"}
   TOOL_RESULT is_error=true  "This command requires approval"
   {"subtype":"permission_denied"}
   {"type":"result","is_error":false,"subtype":"success"}
   ```

   即:请求"成功"返回,但工具其实没跑,模型只能回答"这条命令被权限拦下了,需要你批准"。用户既看不到授权提示,也没有点同意的入口。

### 为什么必须用 hook(已排除的方案)

调研本机 `claude` CLI(v2.1.266)`--help` 与二进制字符串,确认:

- `--permission-prompt-tool` 存在,但要求**一个已连接的 MCP 工具**才能应答;传入不存在/非 MCP 的名字会直接报错:
  `MCP tool AskUserPermission (passed via --permission-prompt-tool) not found`。
  走这条路要在 Go 后端里实现并托管一个 stdio MCP server,复杂且无收益 → **不采用**。
- `--permission-prompts host` 同样把决定权交给"MCP server / SDK host",裸子进程无法应答 → 仍自动拒绝 → **不采用**。
- `--dangerously-skip-permissions` / `--permission-mode bypassPermissions` 直接放弃"只读"安全边界,与 README 的安全设计冲突 → **不采用**。
- `--permission-mode plan` 会连读操作也要审批,弹窗数量不可接受 → **不采用**。

**唯一可从后端进程控制的入口是 `PreToolUse` hook**:CLI 命中 hook 时会阻塞等待其 stdout,hook 打印
`{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"allow"|"deny","permissionDecisionReason":...,"updatedInput":{...}}}`
即可裁决。字段名已在二进制中核对存在(`hookSpecificOutput` / `permissionDecision` / `permissionDecisionReason` / `updatedInput` / `hookEventName`),`additionalContext` 亦为合法输出字段。

因此授权链路为:**CLI → PreToolUse hook(curl 本机后端)→ 后端 SSE → 浏览器弹窗 → 用户点同意/拒绝 → 后端 → hook stdout → CLI**。

## 2. 开发目标

1. 聊天区在流式输出、消息增减、弹出/关闭授权框时**自动滚到底部**;用户手动上滚查看历史时**不打断**(暂停跟随),回到底部后恢复跟随。
2. 把分身的工具授权请求**代理到前端**,用户可看到"哪个工具、什么参数"并点击**同意 / 拒绝**;裁决真实回传给 CLI,不再静默拒绝。
3. 保持只读安全边界:**只读工具自动放行**,仅写文件 / 删除 / git 写操作 / 越出授权目录 / 敏感 Bash **才弹窗**;授权粒度为**单次**(本次确认不做"始终允许",避免持久化风险)。

## 3. 实现范围

本次实现:

- 前端:聊天容器 ref + 滚动跟随(智能 pinned-to-bottom)。
- 后端:新增 `internal/permission` 授权中枢(内存 pending 表 + channel 回传)、`/api/permissions/*` 路由、`PreToolUse` 决策分类器。
- 后端:注入 `--settings` 内联 JSON,注册 `PreToolUse` hook 指向随服务启动的 hook 脚本。
- 分身运行:改为 stream-json **双向**(`--input-format stream-json`),保持 stdin 打开直到本轮结束,以便 hook 阻塞期间进程存活。
- 前端:授权卡片(工具名、参数摘要、同意/拒绝)、SSE 新增 `permission_request` / `permission_resolved` 事件。
- 超时与断线保护:用户不响应 → 默认拒绝;SSE 断开 → 立即拒绝并释放 hook。

本次暂不实现:

- "始终允许同类操作"与规则持久化(下一步按需评估)。
- 授权审计报表 / 管理界面。
- MCP 形式的 permission prompt tool。
- 多用户并发隔离(当前按 IP 分组,授权中枢按 `request_id` 全局路由,详见 §7 待确认)。

## 4. 技术设计

### 4.1 授权链路时序

```
claude -p ... --settings '{"hooks":{"PreToolUse":[{"hooks":[{"type":"command","command":"<bin>/avatar-hook --addr 127.0.0.1:8080"}]}]}}'
      │  需要调用 Write/Bash...
      ├─ stdin(JSON) → avatar-hook: {hook_event_name:"PreToolUse", tool_name, tool_input, session_id, cwd, transcript_path}
      │                   │ POST /api/permissions/request {request_id, tool_name, tool_input, conversation_id?}
      │                   ▼
      │            permission.Hub.Create(req) → 挂起 channel
      │                   │ SSE permission_request → 浏览器弹窗
      │                   ▼
      │            用户点击 → POST /api/permissions/decide {request_id, behavior:"allow"|"deny"}
      │                   ▼
      │            Hub.Decide → 唤醒 channel
      │   ← 200 {"permissionDecision":"allow"|"deny"}
      └─ stdout → CLI 放行/拒绝,工具真正执行或明确失败
```

关键点:hook 是**同步阻塞**的,其超时预算必须 ≥ 人类反应时间;故 hook 内部 HTTP 等待设 `AVATAR_PERMISSION_WAIT_SEC`(默认 120s),并在 CLI 侧把 hook `timeout` 配到大于该值(建议 150)。分身整体超时 `AVATAR_TIMEOUT_SEC`(300s)仍是硬上限。

### 4.2 决策分类器(决定"要不要弹窗")

`permission.Classify(toolName string, toolInput map[string]any, roots []string, workspaceRoot string) → (Decision, Reason)`

- `Decision` ∈ `allow`(自动放行,不弹窗) / `ask`(弹窗) / `deny`(自动拒绝,不弹窗)。
- 只读放行:`Read`、`Grep`、`Glob`、`LS`、`NotebookRead`、`WebFetch`(可选关闭)。
- 读类工具仍需**路径校验**:命中 `roots`(授权 code 工作区)或 `workspaceRoot` 之下 → `allow`;越出授权目录 → `deny`(理由写入 `permissionDecisionReason`,模型可见)。
- 写类直接 `deny`(不改成人审,守住只读铁律):`Write`、`Edit`、`MultiEdit`、`NotebookEdit`、`DeleteFile`、`git commit/push`。
- `Bash`:解析命令首词与关键片段
  - 只读命令白名单 `cat/head/tail/ls/find/grep/rg/sed -n/awk/git status|log|diff|show|branch|blame/ls-files/curl -s http://127.0.0.1:8080/api/db/*` → `allow`;
  - 含 `rm|mv|cp|tee|>|>>|chmod|kill|curl -X POST|git commit|git push|npm|go test|docker` → `ask`;
  - 无法判定 → `ask`(默认让人决定,宁可多问不误放)。
- 数据查询类命令(仅访问本机 `/api/db/*`)必须只读:命中 SQL 里 `INSERT|UPDATE|DELETE|DROP|ALTER|TRUNCATE` → `deny`。

> 分类器是纯函数,便于单测;所有规则集中在一张表里,后续可外置到 `agent_config`。

### 4.3 授权中枢 `internal/permission`

```go
type Request struct {
    ID             string         // request_id(由 hook 生成 UUID)
    ToolName       string
    ToolInput      map[string]any
    Summary        string         // 展示用摘要:工具名 + 关键参数(截断 400 rune)
    ConversationID int64
    CreatedAt      time.Time
    ch             chan Decision
}
type Hub struct { mu sync.Mutex; m map[string]*Request }
func (h *Hub) Create(ctx, r) (*Request, error)
func (h *Hub) Wait(ctx, id) (Decision, error)   // hook 侧阻塞
func (h *Hub) Decide(id, behavior, reason) error // 浏览器侧唤醒
func (h *Hub) DropByConv(id int64)              // SSE 断开/会话结束时清挂起项
```

- `Wait` 返回 `Decision{Behavior, Reason}`;ctx 取消(后端重启/进程退出)时按 `deny` 处理。
- 超时未决 → `deny` + `reason:"授权超时,已自动拒绝"`。
- `m` 上限保护(如 200 条)避免异常堆积。

### 4.4 后端接口

```
POST /api/permissions/request   body {request_id, tool_name, tool_input, conversation_id}
                                → 202 {decision:"pending"}  (广播给 SSE)
                                → 若分类器 allow/deny:直接 200 {permissionDecision}
GET  /api/permissions/pending   → {items:[Request...]}  供前端重连后补齐弹窗
POST /api/permissions/decide    body {request_id, behavior:"allow"|"deny", reason?}
                                → {ok:true}
```

以上三个端点**必须绕过 IP 白名单之外仍保持一致性**:沿用 `auth.GinIPAllowlist`(hook 与浏览器同机/同网段,均在 allowlist 内),避免新增未鉴权入口。`/api/permissions/request` 与 `/decide` 只接受 `127.0.0.1` 与已在 `AVATAR_ALLOWED_IPS` 内的地址(由中间件保证),不额外放宽。

### 4.5 SSE 事件扩展(`/api/question`)

新增两类事件,与现有 `chunk/rejected/error/done` 并列:

```
data: {"type":"permission_request","request_id":"...","tool_name":"Bash","summary":"curl -X POST ...","created_at":"..."}
data: {"type":"permission_resolved","request_id":"...","behavior":"allow","by":"user"|"auto"|"timeout"}
```

`permission_request` 通过 `Question` 请求上下文绑定的 `convID` 定向推送:handler 在开始流时 `hub.Subscribe(convID)`(实现为 `map[int64][]chan Request`,广播 + 单播结合),`Ask` 返回/ctx 结束时取消订阅并 `DropByConv`。

### 4.6 agent 运行改造

- 追加参数:`--settings <内联 JSON>`(注册 hook)、`--input-format stream-json`(读 stdin)、保留 `--output-format stream-json --include-partial-messages --verbose`。
- 用户消息改为写 stdin:`{"type":"user","message":{"role":"user","content":[{"type":"text","text":<history+question>}]}}`,写完**不关闭** stdin,直到读到 `{"type":"result"}` 或 ctx 结束,避免 hook 阻塞期间 CLI 因 EOF 提前退出。
- 解析新增事件:`{"subtype":"permission_denied"}`(模型未获授权)与 `assistant` 中的 `tool_use` 块 → 转成 SSE `tool` 事件(前端展示"正在读取 xxx",提升可观测性)。
- hook 脚本落地:`scripts/avatar-hook`(Go 独立 `main` 或 shell + curl 二选一)。**选择 Go**:新建 `server/cmd/avatar-hook/main.go`,`start.sh` 用 `go build -o bin/avatar-hook ./cmd/avatar-hook` 产出固定路径,写进 `--settings`,避免 shell 引号转义问题;hook 只做"读 stdin → POST → 原样回写 decision",不含业务判断。
- `Result` 结构增加 `Denied []DeniedEvent`,供 service 记录状态。

### 4.7 服务接线

- `config.Config` 新增:`PermissionWaitSec int`(默认 120)、`HookBin string`(默认 `bin/avatar-hook`)、`PermissionEnabled bool`(默认 true,关闭时自动放行只读、拒绝其余,退回 v0.0.4 行为)。
- `service.Service` 持有 `Permissions *permission.Hub`;`Ask` 传入 `convID` 与分类上下文。
- `main.go`:构造 hub → 注入 svc → 注册路由 → 退出时 `hub.CloseAll()`。

### 4.8 前端自动滚动

```jsx
const boxRef = useRef(null)
const [pinned, setPinned] = useState(true)   // 是否跟随底部
const onScroll = () => {
  const el = boxRef.current; if (!el) return
  setPinned(el.scrollHeight - el.scrollTop - el.clientHeight < 40) // 40px 容差
}
useEffect(() => { if (pinned) boxRef.current.scrollTop = boxRef.current.scrollHeight },
          [chatLog, pending, permissionReq, loading])
```

- 滚动容器 `.chatbox` 与 textarea 分离;发送后强制 `pinned = true` 并滚到底。
- 打开历史会话、切换 tab 后同样滚到底。
- `.chatbox` 高度改为 `flex:1; min-height:0`,页面改为 `height:100dvh` 纵向布局,使聊天区占满剩余空间(现 `46vh` 在小屏下太矮)。

### 4.9 前端授权卡片

- 状态 `permissionReq`(队列首条)+ `permissionQueue`。重连时先 `GET /api/permissions/pending` 补齐。
- 渲染在输入框上方、聊天区底部(始终在可视区内),内容:工具名、参数摘要、"仅本次允许"文案、`同意` / `拒绝` 按钮。
- 点击 → `POST /api/permissions/decide`,本地出队;后端返回 `permission_resolved` 时同步出队(幂等:按 `request_id` 去重)。
- 卡片显示期间禁用发送按钮,避免并发提问抢占同一分身进程。
- 倒计时提示剩余 `PermissionWaitSec`,超时自动按拒绝处理。

数据:`messages` 表无需变更(授权过程为瞬态,不落库);`db/schema.sql` 不动。
依赖:无新增。`request_id` 用标准库 `crypto/rand` 生成 16 字节 hex(`google/uuid` 未在 go.mod 中声明,不为此新增依赖)。

安全影响(重要):

- 原本"物理上无法批准"→ 现在**局域网内用户可批准 Bash**。因此分类器必须默认保守:写类一律 `deny`,只读白名单才 `allow`,其余 `ask`,且 `ask` 只放行**单次**。
- hook 端点只在本机监听,且必须经过 IP allowlist;`AVATAR_ALLOWED_IPS` 为空(=放行全部)时,应在启动日志打印告警,提示"授权接口暴露给全网段"。
- 摘要展示前对参数做截断与去敏感化(过滤 `password=`/`token=`/`ANTHROPIC_*`)。

## 8. 实测结果(2026-09-09)

| 场景 | 期望 | 实测 |
|---|---|---|
| 只读工具(Read/Grep)在授权目录内 | 自动放行、不打扰 | 221 chunk、`permission_request` **0 次**、`done` 正常 |
| Bash 非白名单命令 | 弹窗 → 同意后真正执行 | 弹窗 1 次,`decide allow` → `resolved by=user`,续流 76 chunk 到 `done` |
| Bash 命令点拒绝 | 拒绝回传 CLI | `deny` 正确回传,resolved `by=user` |
| 灾难命令(`rm -rf /` 等) | 直接拒绝不打扰 | 单测覆盖 |
| 越权目录读取 | 弹窗(收紧,不静默放行) | 单测覆盖 |
| 经 vite 代理(:5173) | 事件透传 | `permission_request` + `decide` 均正常 |
| 未启用授权(`AVATAR_PERMISSION_ENABLED=0`) | 不静默提权 | 统一 deny |

另注:接入 hook 后,CLI 不再产生 `{"subtype":"permission_denied"}`(该事件是「无人可应答 → 自动拒绝」的产物,现由 hook 应答)。

实测还确认 hook 的 stdin 含 `session_id / cwd / tool_name / tool_input / permission_mode`,CLI 会阻塞等待 hook 退出并采纳其 stdout;`deadline` 恰为 `created_at + 120s`。
